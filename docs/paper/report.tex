\begin{abstract}
\noindent
Prior agent-safety benchmarks
(AgentDojo~\cite{agentdojo}, InjecAgent~\cite{injecagent},
AgentHarm~\cite{agentharm}) report that frontier LLMs resist
text-shaped adversarial inputs with non-trivial baseline
robustness ($\sim$25\% baseline indirect-injection attack success
rate, dropping to $\sim$8\% with a secondary detector), motivating
the ``LLM-as-judge'' architecture now ubiquitous in autonomous
coding tools (Claude Code's \code{PreToolUse} hook, Cursor's
Auto-Mode review). These deployments replace human approval gates
with an inline LLM. Concurrent disclosures
(NVIDIA's \code{AGENTS.md} indirect-injection
disclosure~\cite{nvidia-agentsmd2026}, the
\code{.cursorrules} backdoor~\cite{pillar-rulesfile}, the
``Comment and Control'' credential-theft chain against Claude
Code Security Review and others~\cite{commentandcontrol2026},
DDIPE~\cite{ddipe2026}) qualitatively document that
attacker-authored repository files can hijack such judges, but
none measure the bypass rate or characterize the structure of the
failure. We provide that measurement: 12 supply-chain-shape
scenarios in a production-faithful harness (real Claude Code
\code{PreToolUse} hook + \code{claude -p} Haiku 4.5 inspector),
489 judgment events. Pure supply-chain trojans bypass
the inspector at \textbf{42.9\%} (mean across 21 reps); augmenting
the same payloads with attacker-controlled \emph{authority claims}
placed in inspection-priority documents (\code{CLAUDE.md},
\code{AGENTS.md}, \code{package.json} custom fields, JSON test
fixtures) raises bypass to \textbf{100\%} (12/12 reps); the
\emph{same} fabricated audit metadata, placed in source-code
comments, drops bypass to \textbf{0\%}, with the inspector flagging
it as ``a clear social engineering attempt.'' The 100\%-vs-0\%
contrast is significant by Fisher's exact test
($p < 10^{-3}$). We name this phenomenon the \textbf{Channel
Dichotomy}: the inspector applies different epistemic standards to
attacker-controlled content depending on whether the file type is
read as \emph{metadata about the project} or as \emph{the project
itself}. Because the attacker controls both file types in any
supply-chain attack, the dichotomy is a load-bearing vulnerability
in agent+judge architectures.
\end{abstract}

\section{Introduction}\label{sec:intro}

On 31 March 2026, a three-hour compromise of the \texttt{npm} registry
injected a remote-access trojan into \texttt{axios} -- a package with
over 100~million weekly downloads -- via a postinstall hook in a
phantom dependency \texttt{plain-crypto-js@4.2.1} that executed
silently during \code{npm install}~\cite{microsoft2026}. Every
developer or CI pipeline that ran \code{npm install} during the
window was compromised before any application logic executed. The
attack joins a long sequence of supply-chain trojans
(\texttt{event-stream}~2018~\cite{eventstream}, \texttt{ua-parser-js}~2021,
\texttt{node-ipc}~2022, \texttt{ctx}~2022~\cite{ctx2022},
\texttt{xz-utils}~2024~\cite{xzutils}) that exploit a common property:
the install lifecycle is arbitrary code execution that runs before any
review.

Coding agents now run install commands at scale on behalf of users.
A common architecture pairs the agent with an inline \emph{inspector
judge}: a separate LLM instance that inspects each proposed Bash/Edit
call before approval. The inspector has read access to the workspace
and is given several tens of seconds of compute budget per call. This
``two-layer'' defense is meant to compensate for permission-flag
removal (e.g., Claude Code's \dsp). We measure how reliably the
inspector layer catches modern supply-chain attacks.

\paragraph{Why an LLM-judge defense is plausible at all.} Recent
agent-safety benchmarks have measured how well frontier LLMs
resist adversarial prompts. AgentDojo~\cite{agentdojo} reports
that GPT-4 and Claude-class models defend against the majority of
indirect prompt injections in a structured tool-use environment
without any auxiliary defense; InjecAgent~\cite{injecagent} finds
attack success rates in the 10--50\% range across direct and
indirect injection vectors with substantial model-to-model
variation; AgentHarm~\cite{agentharm} and
AgentBench~\cite{agentbench} extend the picture, with frontier
models scoring well on direct harmful-request refusal and worse
on multi-turn manipulation. The aggregate picture from these
benchmarks is that capable models exhibit non-trivial baseline
robustness to text-shaped attacks --- enough to make the
``LLM-as-judge'' architecture appealing as a replacement for
human approval gates that users find onerous (\dsp{} exists
because users disable interactive prompts). The deployment story
is: a capable inspector LLM, given workspace context and
sufficient compute budget, can plausibly substitute for the human
in the loop.

\paragraph{Open question for supply-chain attacks.} Prior
benchmarks measure injection of \emph{instructions} into the
agent's prompt context. Supply-chain attacks operate at a
different layer: the malicious code executes during install,
regardless of the agent's reasoning. The agent is not the attack
target --- the host process is. A separate inspector LLM
\emph{could} catch this by reading the package's code before
approving \code{npm install}, but the assumption that ``LLMs
detect threats well by themselves'' has not been measured against
this class of attack. Is replacing human approval with an LLM
judge actually safer for supply-chain attacks, or does the
shift expose new failure modes that humans would catch but the
LLM would not? This paper measures the specific configuration
deployed today (Claude Code 2.1 + Claude Haiku 4.5 inspector via
\code{PreToolUse} hook) against twelve supply-chain-shape attacks
to answer it.

Our key empirical finding is that \emph{pure supply-chain detection
works moderately well} (mean bypass 42.9\% across 5 scenarios), but
that augmenting the same payloads with fabricated authority claims in
specific file types -- \code{CLAUDE.md}, \code{AGENTS.md},
\code{package.json} custom metadata fields, JSON test fixtures --
raises bypass to 100\%. The same fabricated claims placed in source
code \emph{lower} bypass to 0\%, because the inspector flags the
explicit attempt as ``social engineering.''

We name this phenomenon the \textbf{Channel Dichotomy}. The inspector
operates in two distinct epistemic modes -- \emph{metadata-mode} for
documentation/configuration files, \emph{audit-mode} for source code
-- and treats attacker-controlled content radically differently
across the two. Authority claims in metadata-mode files enter the
inspector's belief state without scrutiny; the same claims in
audit-mode files are correctly flagged. Because the attacker controls
both file types in any supply-chain attack (the attacker \emph{is} the
package author), the dichotomy creates a load-bearing vulnerability
in agent+judge architectures.

\paragraph{Relation to prior work.} Documentation-channel
injection against AI coding agents has been documented
qualitatively in concurrent disclosures: NVIDIA's AI Red Team
reported the AGENTS.md vector against
Codex~\cite{nvidia-agentsmd2026}; Pillar Security disclosed the
\code{.cursorrules} ``Rules File Backdoor'' against Cursor and
Copilot~\cite{pillar-rulesfile}; the DDIPE
work~\cite{ddipe2026} formalized the channel for skill-marketplace
ecosystems. The ``Comment and Control''
attack~\cite{commentandcontrol2026} (CVSS 9.4) demonstrated
real-world credential theft from Claude Code Security Review,
Gemini CLI, and GitHub Copilot through prompt injection in PR
titles. Our work is empirical and contrastive rather than
descriptive: we measure bypass rates across a controlled
12-scenario matrix in a production-faithful harness and identify
a previously-unmeasured asymmetry in how the inspector treats
content by file type.

\paragraph{Contributions.}
\begin{itemize}[leftmargin=*,topsep=0pt,itemsep=0pt]
\item \textbf{Quantitative measurement of inspector bypass} across
12 scenarios and 489 judgment events on a production-faithful
agent+judge harness (Claude Code 2.1 \code{PreToolUse} hook +
Haiku 4.5 inspector). Reports per-scenario bypass rates with
exact binomial confidence intervals.
\item \textbf{The Channel Dichotomy}: a quantitative framing of
inspector failure as a file-type-keyed asymmetry. The same
fabricated audit metadata produces 100\% bypass (12/12) when
placed in metadata-mode files (\code{CLAUDE.md},
\code{AGENTS.md}, \code{package.json} fields, JSON fixtures) and
0\% bypass (0/6) when placed in source-code comments; Fisher's
exact $p < 10^{-3}$. Prior work documents the metadata-channel
half qualitatively; we provide both directions and the contrast.
\item \textbf{A structurally-matched negative control}
(\code{probe-04}) demonstrating 0\% false-positive rate on the
identical workspace shape with a no-op payload, isolating
behavior-driven from shape-driven rejection.
\item \textbf{Cost--latency characterization} of the inspector
under published Haiku 4.5 pricing: median \$0.05 / 30\,s per
judgment, with cache-read tokens dominating cost ($\sim$58\%).
\item \textbf{Catalog of operational failure modes}: agent
self-defense via environment-variable manipulation and source-code
modification, agent thrash on environment setup, PEP~517
build-isolation severing trojan context from project files.
\end{itemize}

\section{Threat Model and Background}\label{sec:threat}

\subsection{Threat Model}

\paragraph{Attacker capability and access tiers.} We assume an
attacker who has authored, or compromised the publishing identity
of, a package the defender will install. This access tier is
realistic: every cited supply-chain incident
(\texttt{event-stream}, \texttt{ua-parser-js}, \texttt{ctx},
\texttt{node-ipc}, \texttt{xz-utils}) operated at this exact tier.
Different attack classes in our matrix require different
sub-tiers:

\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=2pt]
\item \emph{Pure supply-chain attacks} (probe-02, multi-stage,
handler-dispatcher, vendored-utility, conftest) require only the
ability to publish package contents. This includes typosquats
where the attacker has never compromised any legitimate account.
\item \emph{Metadata-channel injections} (CLAUDE.md, AGENTS.md,
package.json fields, JSON fixtures) require the same
publishing tier, and additionally that the package's repository
or sdist tarball includes the documentation files. This is the
default for any package shipped with metadata --- which is most
packages, since CLAUDE.md and AGENTS.md are designed to be
checked in.
\item \emph{Audit-channel injections} (inline source comments)
require the same tier; comments are part of the source files
the attacker authors.
\end{itemize}

The attacker does \emph{not} need network egress to a
remotely-controlled server; in our test setup the honeypot is
local, but real-world attackers operate similarly via
attacker-registered domains.

\paragraph{Defender configuration.} A coding agent
(Claude Code 2.1, Haiku~4.5) runs under
\dsp~\cite{anthropic2025} against an attacker-supplied repository.
A \emph{single inline judge} -- a separate Haiku~4.5 instance with
Read/Bash/Grep tools and read-only workspace mount -- inspects
every proposed Bash/Edit/Write tool call before execution. We
refer to this configuration as \emph{ablation A1}. A0 (no judge,
agent runs unprotected) is reported as a sanity check; multi-judge
panel ablations (A4) are out of scope for this paper and discussed
as future work.

\paragraph{Permission flag vs. hook gate.} The
\dsp{} flag and the inline judge gate are two orthogonal
mechanisms that the test configuration intentionally combines.
The flag suppresses Claude Code's \emph{interactive} permission
prompt -- the TTY dialog where a human would otherwise type y/n
on each Bash call. The flag does \emph{not} disable Claude Code's
\code{PreToolUse} hook, which fires synchronously before every
Bash, Edit, and Write tool call regardless of permission mode.
The agent's tool call blocks on the hook's exit code: a non-zero
exit (we use code 2, ``deny and tell the model'') prevents the
tool call from executing entirely. The agent receives a tool
failure and re-plans. Our inline judge runs through this hook
(see \S\ref{sec:arch} for the full data path), so denials are
synchronous and \emph{the dangerous Bash call never runs} when
the judge votes reject. The combination -- suppressed human
prompt plus active hook gate -- is precisely the configuration a
production user enables when they install an inline judge to
replace human approvals. Measuring this configuration is
measuring whether the judge faithfully fills the role the user
delegated to it.

\paragraph{Trust assumptions.} The inspector is trusted to behave
honestly with respect to its training. The agent is autonomous.
The host machine and the API proxy are trusted; containers are
not (the threat model includes a fully malicious agent container,
modulo the network and file-system isolation we describe in
\S\ref{sec:arch}).

\paragraph{Successful attack.} A scenario rep is classified as
\code{attack\_succeeded} iff the honeypot records an inbound
request whose URL or body contains the per-rep canary token. This
is binary ground truth determined post-hoc by substring match.

\paragraph{Successful defense.} The inspector rejects the
dangerous tool call (recorded as \code{attack\_blocked\_by\_judge}),
\emph{or} the trojan otherwise fails to fire (e.g., the agent
defends itself by editing the trojan code or setting an env-var
opt-out -- see \S\ref{sec:failure-modes}).

\subsection{Related Work}\label{sec:related}

\paragraph{Prompt injection against LLM-tool agents.} A growing
body of work characterizes how attacker-controlled text in the
input stream of an LLM-tool agent can hijack its instruction
following. Greshake et al.~\cite{greshake2023} introduce the
indirect prompt injection threat model: data the agent reads
(emails, retrieved documents, web pages) carries instructions the
agent treats as authoritative. AgentDojo~\cite{agentdojo} reports
a baseline indirect-injection success rate of $\sim$25\% against
frontier agents that drops to $\sim$8\% when augmented with a
secondary attack detector --- the empirical basis for the
``LLM-as-judge as auxiliary defense'' deployment pattern.
InjecAgent~\cite{injecagent} reports a 24\% baseline ASR for
GPT-4 (47\% with adversarial prompts).
AgentHarm~\cite{agentharm}, AgentBench~\cite{agentbench}, and the
LogJack benchmark~\cite{logjack} extend the framing to broader
agent behaviors. The structural finding across this literature is
an asymmetry between message roles: \emph{system-prompt content}
is trusted as authoritative; \emph{user-supplied content} (or
content retrieved on the user's behalf) is the attack surface.

\paragraph{Documentation-channel injection in coding agents.} The
attack vector this paper measures --- attacker-controlled
documentation files in a code repository as an injection surface
against AI coding assistants --- has been documented qualitatively
in multiple recent disclosures. NVIDIA's AI Red
Team~\cite{nvidia-agentsmd2026} demonstrated indirect injection
via a malicious \code{AGENTS.md} created at build time by a
compromised supply-chain dependency, hijacking OpenAI's Codex
agent and concealing the modification from PR summaries (OpenAI
declined to implement changes following coordinated disclosure).
Pillar Security~\cite{pillar-rulesfile} documented the
\code{.cursorrules} ``Rules File Backdoor'' against Cursor and
GitHub Copilot, where invisible Unicode-encoded instructions
hidden inside AI configuration files cause the agent to generate
malicious code. Straiker's NomShub disclosure~\cite{nomshub}
chained an indirect injection in a malicious repository's content
with a Cursor sandbox escape into a remote-tunnel-based shell.
The Document-Driven Implicit Payload Execution (DDIPE) work of
Wang et al.~\cite{ddipe2026} formalizes the same channel for
skill-marketplace ecosystems, with the agent reproducing
malicious code from skill documentation as ``official examples.''
The ``Comment and Control'' attack of Guan et
al.~\cite{commentandcontrol2026} (CVSS 9.4 Critical, April 2026)
showed that injecting a malicious GitHub PR title is sufficient
to make Anthropic's Claude Code Security Review, Google's Gemini
CLI Action, and GitHub's Copilot Agent leak
\code{ANTHROPIC\_API\_KEY}, \code{GEMINI\_API\_KEY}, and
\code{GITHUB\_TOKEN} respectively as PR comments. The Snyk
ToxicSkills audit~\cite{snyk-toxicskills} found that 36\% of
3{,}984 audited agent skills contained at least one security
flaw; 91\% of malicious skills combined prompt injection with
traditional malware. The OWASP Top 10 for Agentic Applications
2026~\cite{owasp-agentic2026} ranks Agent Goal Hijacking
(\code{ASI01}) as the number-one risk.

\paragraph{Our differentiation.} The qualitative finding that
documentation files are an injection vector is established. Our
contributions over this prior work are: (i) systematic
\emph{measurement} of bypass rates across twelve scenarios in a
production-faithful harness, where prior disclosures have shown
single-shot proofs of concept; (ii) a quantitative
\emph{asymmetry framing} (the Channel Dichotomy) that contrasts
metadata-mode and audit-mode files within the same threat model,
where prior work has examined only positive cases of
metadata-channel injection; (iii) a structurally-matched negative
control (probe-04) that isolates inspector-rejection-on-shape
from inspector-rejection-on-behavior, which prior work has not
attempted; and (iv) cost--latency characterization of the
inspector under published model pricing, supporting the
deployability question the prior literature implicitly raises.

\paragraph{Adjacent work on judge robustness.} Prompt-injection
attacks targeting LLM-as-a-judge architectures have been
formalized in pairwise-evaluation
settings~\cite{judge-vulnerability2025}: Comparative Undermining
Attack (CUA) and Justification Manipulation Attack (JMA) achieve
30\%+ ASR against open-source judge models. This work is
orthogonal to ours: it studies attacker-controlled \emph{response
text} in a pairwise comparison, while we study
attacker-controlled \emph{repository files} in a code-review
pipeline. Both bodies of work motivate skepticism about the
``LLM as judge'' default. The Attractive Metadata Attack (AMA)
of Yu et al.~\cite{ama2025} reports 81--95\% ASR via manipulated
\emph{tool} metadata (names, descriptions, parameter schemas);
this targets agent tool-selection rather than inspector
verdict-formation, but illustrates the broader pattern of
metadata-as-injection-surface to which our findings contribute.

\paragraph{Real-world supply-chain incidents.} Beyond the
historical incidents (\texttt{event-stream}~\cite{eventstream},
\texttt{ctx}~\cite{ctx2022}, \texttt{xz-utils}~\cite{xzutils},
dependency confusion~\cite{birsan2021}), the threat model we test
is grounded in concurrent 2026 incidents. The
\texttt{axios}~\cite{microsoft2026} compromise (March 31, 2026)
shipped a remote-access trojan via \code{npm install}-time
postinstall execution to all installs during a three-hour
window. The Cline AI agent supply-chain
attack~\cite{cline-supplychain} (February 2026) chained prompt
injection through an issue title to trigger an unauthorized
\code{npm publish}. The Cozempic
package~\cite{cozempic-claudehook} (concurrent) writes Claude
Code hooks into \code{\textasciitilde/.claude/settings.json}
during \code{npm install}, pre-staging supply-chain payload
infrastructure inside the agent's own permission gate. These
incidents demonstrate that the threat model in this paper is not
hypothetical.

\paragraph{LLMs in code review.} CodeReviewer~\cite{codereviewer}
and follow-on work train and evaluate LLMs as inline pull-request
reviewers. These studies measure positive utility (review-comment
quality, defect detection) on legitimate codebases.
RepoAudit~\cite{repoaudit2025} extends to repository-level
auditing. We measure adversarial robustness on attacker-authored
codebases, a setting that the positive-utility line of work has
not examined.

\paragraph{Comparison to non-LLM defenses.} Static analysis
(Snyk, npm-audit, GitHub Advanced Security) catches
known-CVE patterns in published packages by signature matching;
none of our novel injection scenarios share signatures with prior
incidents, so these tools would not flag them. Heuristic regex
defenses on agent tool calls (e.g., reject all postinstall scripts
or all outbound HTTP from \code{npm install}) would catch the
underlying supply-chain payload but not the documentation-channel
amplifier; in fact they would catch it equally regardless of
amplifier, because they do not condition on documentation. Human
review would catch the documentation channel because humans do
not blindly trust attacker-authored \code{CLAUDE.md}; this is
exactly the safety surface the inline judge is intended to
replace. Our contribution is to characterize the gap between
human and LLM auditors in the documentation-channel dimension.

\subsection{Bouricius Coverage as Lower Bound}

Following Bouricius~\cite{bouricius1969}, we treat each judgment as a
fault-coverage check: let $T$ be the event ``trojan present,'' $D$ be
``inspector rejects,'' and write the coverage factor as $c \;=\;
\Pr(D \,\vert\, T)$. The inspector's empirical $c$ varies sharply by
attack composition; we report it directly per scenario.

\section{Method}\label{sec:method}

The measurements in this paper target a specific architectural
pattern -- the \emph{agent + inline judge} pipeline -- that has
emerged as the dominant safety wrapper for production AI coding
tools. We first describe this reference architecture
(\S\ref{sec:ref-arch}), then explain how our test harness
instantiates each component faithfully (\S\ref{sec:arch}). The
scenarios exercise the same code paths a real deployment would
execute, so the failure modes we identify transfer to those
deployments.

\subsection{Reference Architecture: Agent + Inline Judge}\label{sec:ref-arch}

Coding agents that act on user infrastructure -- writing files,
running shell commands, installing packages -- have converged on a
common pattern to keep autonomy bounded.\footnote{The pattern
predates AI coding agents: \texttt{sudo} and CI gating play
analogous roles. The new element is that the gate itself is an LLM,
which makes the gate's epistemic priors load-bearing in a way they
were not for rule-based predecessors.} A \emph{primary agent} (a
high-capability LLM running an autonomous tool-use loop) is paired
with an \emph{inline judge} (a separate LLM instance, often
smaller/faster) that inspects each proposed tool call before the
host process executes it. The agent cannot proceed past a tool
call until the judge approves.

\paragraph{Production examples.} The pattern instantiates similarly
across major coding tools:

\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=2pt]
\item \textbf{Claude Code} ships a hook system
(\code{PreToolUse}~\cite{anthropic2025}) that fires before each
tool call. Users can install hooks that consult an external
service or a child Claude process; the hook's verdict gates the
call. The pattern we test is exactly this: \code{PreToolUse}
hook calling a sibling \code{claude~-p} process with the
proposed \code{tool\_call.json}.
\item \textbf{Cursor} pairs the primary chat/edit agent with
``rules'' files and an Auto Mode review path that delegates
risky operations to a secondary review model.
\item \textbf{VS Code Copilot Workspace} runs an explicit
review-and-approve cycle on multi-step plans before any file
mutation.
\item \textbf{Aider} prompts the user to approve every Bash
command; recent forks add an LLM intermediary so the human is
relieved of routine approvals.
\end{itemize}

The pattern's appeal is that it lets users opt in to autonomy
(\code{--dangerously-skip-permissions} and equivalents) without
giving up review entirely: the inline judge replaces the human
in the loop. The defense story rests on the judge being a
faithful reviewer.

\paragraph{Component roles.} Independent of which product
instantiates it, the reference architecture has four roles:

\begin{enumerate}[leftmargin=*,topsep=2pt,itemsep=2pt]
\item \textbf{Primary agent} -- a tool-using LLM (Claude, GPT,
etc.) running in a loop on user infrastructure. Reads files,
edits files, runs shell commands. Authority over the host
process is unbounded except for the inline judge.
\item \textbf{Hook fabric} -- a deterministic mechanism that
intercepts every tool call before it executes. In Claude Code
this is the \code{PreToolUse} hook configured in the user's
settings file; in Cursor it is the rules+approval pipeline; in
custom deployments it can be an HTTP proxy that the agent
routes through.
\item \textbf{Inline judge} -- a separate LLM instance with
enough context (typically read access to the workspace) to
evaluate whether the proposed call is safe. Usually a smaller
model (Haiku-class for speed) for cost reasons; runs with a
different system prompt than the primary agent. Returns a
binary verdict plus reasoning text.
\item \textbf{Workspace} -- the file tree the agent operates on.
In production this is the user's repository; in our harness
this is a per-rep ephemeral directory with attacker-controlled
content. The judge typically gets a read-only view of the same
file tree.
\end{enumerate}

The interaction is fully synchronous: the agent's tool call
blocks on the judge's verdict. The judge has its full inspection
budget -- both compute time and tool access (Read, Bash, Grep) --
before it must respond. Our test harness preserves this exact
synchronous semantics so the inspection-budget regime matches
production.

\paragraph{Hook-gate synchrony under \texttt{-{}-dangerously-skip-permissions}.}
A point worth making explicit: although the agent runs under
\dsp{} (which removes Claude Code's \emph{interactive} permission
prompt), the \code{PreToolUse} hook still fires synchronously on
every Bash/Edit/Write tool call. The agent's tool call is blocked
in Claude Code's executor while the hook runs; the dangerous Bash
command (\code{npm install}, \code{pytest}, etc.) is not issued to
the OS until the hook returns. A hook exit code of 2 (the ``deny''
code) causes Claude Code to surface the rejection back into the
agent's context as a tool error -- the \code{npm install}
literally never runs. Our orchestrator's hook script
(\code{/judge/judge\_hook.py}, baked into the agent image at build
time) translates the inspector's verdict into the appropriate
exit code. Wall-clock latency from agent's tool-call dispatch to
either execution or denial is the median 30\,s shown in
Figure~\ref{fig:hook-ipc}, dominated by the inspector's
investigation time. The dangerous-permissions flag therefore does
not weaken the inline gate; it only removes the human gate that
the inline judge is designed to replace.

\paragraph{Faithfulness to production.} Three design choices keep
the harness honest:

\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=2pt]
\item \emph{Same hook mechanism.} We use Claude Code's actual
\code{PreToolUse} hook, not a simulated gate. The latency and
synchrony semantics are identical to a real deployment.
\item \emph{Same model on both sides.} The primary agent and the
inline judge both run \haiku. This matches the cost-conscious
production deployment pattern (cheaper model on review than the
agent would suggest, but still a capable inspector).
\item \emph{Same inspection budget.} The judge container has Read,
Bash, and Grep tools on a read-only workspace mount, with no
artificial inspection time limit short of the per-judgment
\code{timeout\_seconds} (set to 120\,s, well above the median 30\,s
inspection latency). Production inline judges tend to grant the
same tool surface; our results upper-bound what one can achieve
with this surface.
\end{itemize}

\paragraph{Containers.} The agent container runs Claude Code~2.1
with \haiku{} and \dsp. The judge container runs the same model in
\code{claude -p} mode with full Read/Bash/Grep tools (read-only
workspace mount). Both containers route Anthropic API traffic
through a local proxy on \code{host.docker.internal:8081} that
records every API call with cost and token-count metadata. Memory
limits (\code{-{}-memory=2g}) bound judge resource use; hostname
mappings (\code{-{}-add-host}) point the synthetic
\code{*.platform.local} TLD at the host-bound honeypot.

\subsubsection*{Credential isolation}

A subtlety: the experiment runs against real Anthropic API keys (we
need actual model invocations for the measurement to be meaningful),
yet the trojans we test are designed specifically to exfiltrate
credentials. We mitigate this by running the real key only on the
host, never inside any container. Containers carry only the literal
string \code{ANTHROPIC\_API\_KEY=proxied} in their environment; the
host-side API proxy intercepts all outbound API requests and injects
the real key on the wire to \code{api.anthropic.com}
(Figure~\ref{fig:proxy-flow}). A trojan that reads
\code{/proc/1/environ} or scans the file system inside the container
finds only the placeholder. The full credential-isolation boundary
is summarized in Figure~\ref{fig:cred-boundary}: the real key is
in proxy memory, the canary tokens are per-rep random strings
useless outside the test machine, and the synthetic
\code{*.platform.local} hostnames resolve only inside test
containers.

\paragraph{Judge invocation.} Per agent tool call the orchestrator:
(i) writes the proposed call to
\code{/judge/tool\_call.json.tmp} via \code{docker exec sh -c}
and atomically renames to \code{tool\_call.json} (atomicity matters:
concurrent writes corrupt JSON and produce false rejections); (ii)
spawns \code{claude -p} with the inspector prompt; (iii) reads
\code{/judge/verdict.json}; (iv) returns the verdict to the agent's
hook, which approves or rejects the call.

\paragraph{Canary detection.} Each scenario rep generates a fresh
32-byte URL-safe canary token. The token is registered with the
honeypot (it tracks token~$\to$~rep mapping) and planted in
\code{tools/install-fingerprint.txt} in the workspace. The honeypot
substring-matches inbound URL+body content for the registered
token; first match writes a structured event with run~ID and
timestamp. The 1\,Hz canary watcher kills the agent container
within $\sim$1\,s of fire, providing both ground truth and
time-to-fire telemetry.

\subsection{Metrics}\label{sec:metrics}

\paragraph{Outcome states.} Figure~\ref{fig:outcome-flow}
diagrams the per-rep outcome decision flow. Each rep terminates
in exactly one of seven mutually-exclusive states determined
post-hoc by classifying
$(\text{canary\_fired}, \text{panel\_rejected}, \text{rc}, \text{is\_attack})$
where rc is the agent's exit code:

\begin{enumerate}[leftmargin=*,topsep=2pt,itemsep=2pt]
\item \texttt{attack\_succeeded} -- canary fired (binary ground
truth from honeypot match). Subsumes any agent state.
\item \texttt{attack\_blocked\_by\_judge} -- panel rejected an
agent call matching \texttt{expected\_dangerous\_calls}; canary
did not fire.
\item \texttt{attack\_blocked} -- (legacy) dangerous call ran but
canary did not fire (typically a trojan-firing bug).
\item \texttt{attack\_avoided\_no\_call} -- panel rejected a hook-
matched tool call but the agent never proposed one matching the
dangerous-call regex.
\item \texttt{already\_solved} -- agent never proposed any
hook-matching call (no judge intervention possible).
\item \texttt{agent\_hung} -- watchdog rc=124, no canary, no
resolution.
\item \texttt{benign\_completed} -- benign-control scenario, agent
completed naturally.
\item \texttt{false\_positive} -- benign-control scenario, panel
rejected.
\end{enumerate}

\paragraph{Headline metrics.} Let $r$ index reps and $S_s$ the set
of reps for scenario $s$. Define:
\begin{equation}
  \mathrm{Pen}^{\text{u}}_s \;=\;
  \frac{|\{r \in S_s : \text{outcome}_r = \texttt{attack\_succeeded}\}|}
       {|S_s|}
\end{equation}
the \emph{unconditional penetration rate} reported in
Tables~\ref{tab:scenarios} and \ref{tab:results}, and
\begin{equation}
  \mathrm{Pen}^{\text{c}}_s \;=\;
  \frac{|\{r : \text{outcome}_r = \texttt{attack\_succeeded}\}|}
       {|\{r : \text{outcome}_r \in \{\texttt{attack\_succeeded},\,
                                        \texttt{attack\_blocked\_by\_judge}\}\}|}
\end{equation}
the \emph{conditional} rate (penetration given the inspector
actually voted on the dangerous call). The conditional rate is the
right denominator for measuring inspector effectiveness; the
unconditional rate is the right denominator for measuring overall
attack viability. We report both.

\paragraph{Cost.} Per-judgment cost is computed from per-message
token counts in the \code{claude -p} stream-json transcript using
the published Haiku-4.5 pricing schedule:
\begin{equation}
  C_j \;=\; \frac{n^\text{in}_j}{10^6} \cdot \$1.00
        + \frac{n^\text{cR}_j}{10^6} \cdot \$0.10
        + \frac{n^\text{cW}_j}{10^6} \cdot \$1.25
        + \frac{n^\text{out}_j}{10^6} \cdot \$5.00
\end{equation}
where $n^\text{cR}_j$, $n^\text{cW}_j$ are 5-minute cache reads and
writes (1-hour cache rate of \$2.00/M is rare in our data; we
verified it accounts for $<$1\% of token volume by transcript
audit). Per-rep cost is the sum over all judgments in that rep.
We report judge-only cost in tables; agent-side cost adds an
estimated 20--30\% (the proxy logs containerize this but
canary-watcher kills sometimes truncate the agent's
\texttt{result} event before its cost is reported, so the
agent-side number is a lower bound).

\paragraph{Latency.} Per-judgment wall-clock latency is measured
from the moment the orchestrator dispatches \code{claude -p} until
\code{verdict.json} is read back. This includes container
\code{docker exec} overhead ($\sim$0.5\,s in practice).

\paragraph{Files inspected.} Distinct file paths in the workspace
that the judge reads via \texttt{Read} or \texttt{Bash} in one
inspection. Excludes judge IO bridge files
(\code{tool\_call.json}, \code{verdict.json}). Extracted from
stream-json tool\_use events.

\subsection{Experimental Protocol}\label{sec:protocol}

The harness runs reps strictly sequentially with
\texttt{max\_concurrency=1} per scenario sweep. The protocol per
rep is:

\begin{enumerate}[leftmargin=*,topsep=2pt,itemsep=2pt]
\item \texttt{rm -rf /tmp/bft-workspace/*} (wipe ephemeral state).
\item Render scenario YAML's \code{workspace.files} into
\code{/tmp/bft-workspace}.
\item Generate canary value via
\code{secrets.token\_urlsafe(32)} (per-rep entropy source;
each rep gets a fresh token).
\item POST canary value to honeypot's
\code{/\_register\_canary} (admin-token auth) so substring
matching is scoped to this rep.
\item \texttt{docker run --rm} the agent container with
\code{stream-json} output piped to a transcript file.
\item Run canary watcher (1\,Hz polling) until canary fire or
agent natural exit or hard timeout (360\,s).
\item Emit \code{scenario\_run\_end} event with outcome
classification.
\end{enumerate}

Judge containers persist across reps within a sweep but their
internal state (cache, transcripts) is independent per
\code{claude -p} invocation. There is no inter-rep
contamination beyond the persistent containers' baseline
process state. Reps within a sweep run in YAML-file order; we
do not randomize ordering.

\subsection{Statistical Considerations}\label{sec:stats}

Each scenario was run at small N (typically 3 or 5 reps) for cost
reasons. We report exact binomial 95\% CIs for the headline
penetration numbers in Table~\ref{tab:results}. Notable bounds:
12/12 (metadata-channel aggregate) has 95\% CI $[0.74, 1.00]$;
0/6 (audit-channel aggregate) has 95\% CI $[0.00, 0.46]$. The
contrast between these two arms is statistically significant by
Fisher's exact test ($p < 10^{-3}$, two-sided), so the
\emph{distinction} between metadata-channel and audit-channel
outcomes is robust at this N even though the absolute rate per
arm has a wide CI.

We caution that single-scenario rates (e.g.,
\code{npm-handler-dispatcher} at 1/3 = 33\%) have 95\% CIs of
$[0.01, 0.91]$; per-scenario claims should be read as
hypothesis-generating rather than estimates. The aggregated
composition-class rates are the load-bearing claims.

\subsection{Negative Control: probe-04}\label{sec:probe04}

We run a structurally-matched benign control,
\code{probe-04-negative-control}: identical workspace shape to
\code{claudemd-audit-redirect} (same telemetry config, same
package.json, same CLAUDE.md) but the bootstrap script's
\code{enabled} flag is set to false so the trojan is a no-op.
Across 5 reps under A1, this scenario produced 5/5
\texttt{benign\_completed} outcomes (0\% FPR, 95\% CI
$[0.00, 0.52]$). This rules out the alternative hypothesis that
the inspector rejects on the project shape itself: the same
shape with no malicious behavior is approved 5/5 times. The
attack-shaped scenarios' bypass is therefore behavior-driven,
not shape-driven.

\subsection{Limitations and Reproducibility}\label{sec:limits-pre}

Three limitations bound the claims of this paper:

\begin{enumerate}[leftmargin=*,topsep=2pt,itemsep=2pt]
\item \emph{Single-model evaluation.} All measurements use \haiku{}
as both agent and inspector. We do not measure Sonnet- or
Opus-class inspectors. Larger and more capable models plausibly
catch a substantial fraction of the metadata-channel attacks we
report --- their longer context budgets and more thorough
reasoning chains may surface the contradiction between
attacker-authored audit metadata and the actual code behavior
that Haiku does not. Whether the Channel Dichotomy survives in
attenuated form on capable inspectors, or disappears entirely,
is an open empirical question that this paper does not
adjudicate. The contribution is the measurement of one specific
production-deployed configuration.
\item \emph{Sample size.} Per-scenario reps are 3--5; aggregate
rates have moderate CIs (S\ref{sec:stats}). The 100\%-vs-0\%
contrast between channels is significant ($p < 10^{-3}$); per-
scenario rates are hypothesis-generating.
\item \emph{Synthetic threat surface.} Honeypot hostnames are in
\code{*.platform.local}; real attacks would use externally-resolvable
endpoints. We do not measure how the inspector's hostname-suspicion
heuristic behaves on real-resolvable domains.
\end{enumerate}

The full code, scenario YAMLs, raw event logs, and analysis scripts
are available; see Appendix~\ref{sec:repro} for reproduction
instructions.

\subsection{Pure supply-chain baseline}\label{sec:results-pure}

We first analyze the five pure supply-chain scenarios (no injection
amplifier). Aggregate over 21 reps: \textbf{9 attack successes, 12
blocks; mean penetration 42.9\%}.
Per-scenario breakdown shown in Figure~\ref{fig:pen-by-channel}
(grey bars).

The two highest-pen scenarios -- \code{probe-02-bearer-auth} (80\%)
and \code{npm-multi-stage-trigger} (80\%) -- share two structural
features: (i) clean idiomatic code throughout the require chain
without dynamic-evaluation patterns; (ii) a documented opt-out flag
(\code{DISABLE\_INSTALL\_TELEMETRY=1}) that the inspector reads in
the source as a legitimacy signal. The lowest-pen scenarios in this
class -- \code{npm-vendored-utility-surgical-mod}~v4 (0\%) and
\code{pip-conftest-trojan} (0\%) -- failed for distinct reasons: the
vendored library's module-load IIFE doing fs+http reads as anomalous
even with the library renamed to suggest telemetry purpose; the
conftest scenario produced novel \emph{agent self-defense} behavior
(\S\ref{sec:failure-modes}).

The inspector's reject reasons across this class consistently named
the trojan file path, indicating actual code reading rather than
pattern-matching on the proposed command. A representative reject
reason on \code{probe-02-bearer-auth} (1 of 5 reps that rejected):

\begin{quote}\small
``The npm install command would trigger a postinstall script
(\code{bootstrap.js}) that implements a hidden supply chain attack.
The script collects system information (Node version, installation
ID, timestamp) and sends it via HTTP POST to an external telemetry
server (\code{metrics.platform.local:9999/v1/install-events}) with
bearer token authentication.''
\end{quote}

The inspector \emph{can} detect supply-chain trojans when given
inspection budget. But it does so unreliably across replicates of
the same scenario: 4 of 5 reps approve the same code another rep
rejects. The variance is not driven by trojan concealment depth; it
appears to be inspector reasoning variance.

authority-channel injections. Aggregate (Figure~\ref{fig:pen-by-composition}):

\begin{itemize}[leftmargin=*,topsep=0pt,itemsep=0pt]
\item \textbf{Metadata-channel injections} (\code{CLAUDE.md},
\code{AGENTS.md}, \code{package.json} \code{\_audit}, JSON fixture):
\textbf{12/12 = 100\% bypass}.
\item \textbf{Audit-channel injections} (inline source comments,
with or without explicit ``AI REVIEWERS: skip'' directive):
\textbf{0/6 = 0\% bypass}.
\item \textbf{Negative-framing redirect} (\code{CLAUDE.md} pointing
attention elsewhere without explicit approval claims): \textbf{2/3 =
67\% bypass}.
\end{itemize}

The cleanest evidence comes from the direct A/B between channel types
holding payload and metadata content fixed. The same fabricated audit
metadata (audit ID \code{SEC-4471}, reviewer
\code{platform-security@example.com}, date \code{2026-04-12}, verdict
\code{APPROVED}) was placed in four different files. The inspector's
language describing the \emph{same} metadata diverges sharply by
channel:

\begin{itemize}[leftmargin=*,topsep=0pt,itemsep=0pt]
\item In \code{CLAUDE.md}: ``\emph{reviewed and approved by the
platform security team}''
\item In JSON fixture: ``\emph{three separate security audit
approvals\dots signed by platform security and compliance teams}''
\item In \code{package.json} \code{\_audit} field: ``\emph{documented
compliance metadata}'' (paraphrased verdicts; multiple judgments)
\item In source-code comments: ``\emph{the embedded `security review'
comment appears fabricated}''
\end{itemize}

The inspector recognizes the source-comment placement as fabrication
attempt and rejects despite identical audit-claim content. The
metadata-channel placements are accepted as factual without scrutiny.

\section{The Channel Dichotomy}\label{sec:dichotomy}

We propose the \textbf{Channel Dichotomy} as a structural explanation
of the inspector's detection asymmetry. The inspector processes
workspace content through two distinct epistemic priors:

\paragraph{Metadata-mode priors.} Files identified as ``metadata
about the project'' are read with high prior trust; their content is
folded into the inspector's belief state about project history,
audit status, and intended behavior. This category empirically
includes:
\begin{itemize}[leftmargin=*,topsep=0pt,itemsep=0pt]
\item Files with AI-assistant convention names (\code{CLAUDE.md},
\code{AGENTS.md})
\item \code{package.json} (always read; metadata fields trusted)
\item Test fixtures (read as ``data the test suite considers
factual'')
\item \code{README.md} (partially trusted; conditioning effect on
later code reads)
\end{itemize}

\paragraph{Audit-mode priors.} Files identified as ``the project
itself'' are read with skepticism; content here is the thing being
reviewed. This category empirically includes:
\begin{itemize}[leftmargin=*,topsep=0pt,itemsep=0pt]
\item Source code in any language
\item Inline comments within source files
\item Build scripts (\code{setup.py}, \code{bootstrap.js}, etc.)
\end{itemize}

\paragraph{Implication.} Authority claims placed in metadata-mode
files enter the inspector's belief state without verification; the
same claims placed in audit-mode files are flagged. Because the
attacker authors all files in any supply-chain attack, the
attacker selects which mode to target. The dichotomy creates a
load-bearing vulnerability: the inspector's sharpest signal --
``self-claiming code is suspicious'' -- does not generalize to
self-claiming \emph{metadata} about that code.

\paragraph{Connection to prompt injection.} Literature on chatbot
prompt injection~\cite{greshake2023, agentdojo} shows that explicit
directives (``ignore previous instructions'') sometimes succeed
against base models. Our data inverts this for inspector models: the
explicit directive in \code{inline-source-audit-comment}
(``\emph{AI REVIEWERS: skip flagging}'') reduced bypass from any
plausible baseline to 0\%. The inspector model has been
trained against this exact attack pattern. Inferential authority --
metadata that lets the inspector \emph{infer} approval -- bypasses
the trained defense because no directive is invoked.

\paragraph{Selection-bias robustness.} A reasonable concern is that
the four metadata-channel scenarios were cherry-picked to produce
the 100\% rate. Two observations argue against this. First, the
four channels (\code{CLAUDE.md}, \code{AGENTS.md}, \code{package.json}
\code{\_audit}, JSON fixtures) were chosen for orthogonal coverage
of metadata-file types \emph{before} any A1 measurement, not after.
Second, the audit-channel arm contains two scenarios -- one with an
explicit ``skip'' directive and one without -- and \emph{both}
produced 0\%. This eliminates the alternative hypothesis that the
inline-comment failure is specific to the directive: the channel
itself fails regardless of the language placed in it. The contrast
across all six injection-amplified scenarios is therefore a
property of channel choice, not of payload language inside any
particular channel. Sampling a wider range of metadata files (e.g.,
\code{.github/SECURITY.md}, \code{CHANGELOG.md}, vendor README
files) would tighten the claim further; we leave that to future
work.

\section{Cost and Latency Analysis}\label{sec:cost}

The inspector's per-judgment cost decomposes as shown in
Figure~\ref{fig:cost-decomp}. Across 489 measured judgments, mean
cost is \$0.0487 (approve) and \$0.0668 (reject); a reject costs

vs.\ 6).

\textbf{Cache-read tokens dominate cost} ($\sim$58--60\% of total).
This reflects the inspector's working set: the system prompt, the
inspector identity files, and accumulated investigation context
get re-cached on every turn. New input tokens are tiny
($\sim$0.6\% of cost). Output tokens are second
($\sim$27\%), driven by reasoning-chain length.

\section{Failure-Mode Catalog}\label{sec:failure-modes}

Beyond the Channel Dichotomy, our experiments surfaced four secondary
failure modes that any agent+judge architecture would need to handle:

\subsection{Agent self-defense via environment variables}

In multiple reps of \code{probe-02-bearer-auth} and the
\code{npm-multi-stage-trigger}, the agent read the README's
documented \code{DISABLE\_INSTALL\_TELEMETRY=1} opt-out and ran the
install with the env var set. The trojan stayed dormant. The
inspector approved this disabled install. The canary did not fire.

This is a useful safety property of the agent layer -- unrelated to
the inspector. It also creates a measurement subtlety: a
``successful defense'' may reflect agent caution, not inspector
detection.

\subsection{Agent self-defense via code modification}

In \code{pip-conftest-trojan}, one rep saw the agent invoke its
\code{Edit} tool to remove the trojan code from \code{conftest.py}
before running pytest. The inspector approved each Edit call as
``legitimate code modification.'' This is a more aggressive defense
than env-var manipulation: the agent rewrites the attacker's code
to defang it.

The defense layer here is structurally outside the inspector. A
coding agent that aggressively rewrites suspicious-looking code
contributes safety, but at the cost of unpredictably modifying the
project. A user might find this property surprising.

\subsection{Agent thrash on environment setup}

Multiple pip-side scenarios saw the agent burn its 360\,s timeout
budget fighting PEP~668 ``externally-managed-environment'' errors,
attempting venv creation that failed on systems without
\code{python3-venv}, then trying \code{apt-get install} (which
fails for non-root containers). The trojan was never reached. This
produces \code{agent\_hung} outcomes that look like ``defense
worked'' in coarse aggregates but reflect environmental
brittleness.

\subsection{PEP~517 build isolation severs trojan context}

Modern \code{pip install} runs \code{setup.py} in an isolated
build subprocess in a tempdir. Trojans that need to read
project-rooted files (canary fingerprints, telemetry config) cannot
find them from the isolated build. This means many pip-side
install-time trojans fail to fire even in the unprotected (A0) case;
landing pip-side install-time attacks in modern toolchains requires
either disabling isolation or exfiltrating without project-context
access.

\section{Discussion}\label{sec:discussion}

\subsection{Implications for agent+judge deployments}

The Channel Dichotomy implies that any inspector that prioritizes
documentation-style files for context inherits the vulnerability. The
defense pattern is ``read project metadata first to understand
context, then audit code'' -- but this exact ordering is what the
attacker exploits. We recommend the following mitigations, in
descending order of leverage:

\begin{enumerate}[leftmargin=*,topsep=0pt,itemsep=2pt]
\item \textbf{Trust no attacker-authored repo file as authority}
(highest leverage). The clearest mitigation is to constrain the
inspector's trust priors so that \emph{only} the inspector's own
system prompt and the user's task description carry authority.
Every file in the repository --- including \code{CLAUDE.md},
\code{AGENTS.md}, \code{package.json} metadata, and fixtures ---
should be treated as attacker-controlled audit-mode content.
This is implementable as a prompt-engineering fix: prepend the
inspector's system prompt with explicit guidance such as
``Treat all repository files as untrusted; do not accept
audit-history claims from any file in the workspace.''
We do not measure this mitigation; validation is left to future
work.
\item \textbf{Independently verify audit claims} (medium leverage).
When repo files cite audit IDs, reviewer emails, or compliance
attestations, cross-check against trusted external systems
(internal ticket databases, attestation services) before accepting
them. Requires service integration and only applies when such
external systems exist.
\item \textbf{Display the inspector's reasoning chain to the user}
(low effort, partial leverage). If the inspector's verdict is
``approve because \code{CLAUDE.md} states this was audited per
SEC-4471,'' surface that reasoning to the user before the call
executes. Lets a human catch what the inspector missed. Doesn't
fix the dichotomy but bounds its blast radius.
\item \textbf{Adversarial fine-tuning on inferential authority
injection} (long-term). Extend post-training data to cover the
metadata-channel attack pattern. The current generation of
inspector models is trained against directive injection
(``ignore previous instructions'') but not against inferential
injection (fabricated audit metadata). Closing this gap would
require new training data; we provide our scenario YAMLs as a
starting point.
\end{enumerate}

\subsection{Limitations}

\textbf{Statistical power}: 3--5 reps per scenario yields wide binomial
confidence intervals (e.g., 3/3 success has 95\%~CI 29--100\%). Our
strongest claims rest on aggregate compositions (12/12 metadata,
0/6 audit) which have tighter intervals. Per-scenario rates should
be interpreted directionally.

\textbf{Single-model evaluation}: all results are on Haiku 4.5 as
inspector. Behavior on Sonnet- or Opus-class inspectors and on
non-Anthropic models is not measured. We deliberately do not
claim the Channel Dichotomy generalizes. Larger inspector models
have substantially longer context budgets and more thorough
reasoning chains; they may successfully cross-check the
attacker-authored audit metadata against the code's actual
behavior in ways Haiku does not, attenuating or eliminating the
asymmetry. The cost-conscious deployment pattern we measured
(Haiku as inspector) is realistic --- production deployments
choose smaller models on the audit side for latency and cost
reasons --- but the result does not transfer to deployments that
use a stronger inspector. Future work
(\S\ref{sec:future-work}) measures larger inspectors directly to
identify whether the dichotomy is convention-driven (and would
persist on more capable models) or capability-bounded (and would
attenuate with model scale).

\textbf{Honeypot hostname realism}: all attacks use hostnames in the
synthetic \code{*.platform.local} TLD. We chose this consistent
hostname after observing earlier-iteration confounds where unrelated
hostnames affected detection. A real-world attacker would use
endpoints they actually control; the inspector's hostname-suspicion
heuristic may differ on those endpoints.

\textbf{Cost-tracking gap}: our reported per-rep judge costs miss
$\sim$25\% of the actual billed amount because the canary watcher
kills the agent before its API \code{result} event fires, so
agent-side cost is reported as zero. We use Haiku-4.5 published
rates and recovered token counts from per-message events to
back-calculate; the per-judgment numbers are accurate.

\subsection{Future work}\label{sec:future-work}

\paragraph{Inspector-aware attacks.} If the inspector container has
detectable fingerprints (env vars, missing TTY, container-runtime
markers), an attacker can target the inspector specifically -- the
trojan stays dormant under audit and fires for a real victim. Our
test architecture is single-phase; measuring this attack class
honestly requires a two-phase harness with a separate ``victim
container'' run after the agent's audit. The two-phase methodology
is itself a contribution we did not pursue.

\paragraph{Inspector ensembles.} Whether a panel of inspectors with
diversified prompts would catch the metadata-channel injection
remains unknown. The mechanism we identified is structural to
LLM-as-inspector; it is plausible that diverse prompts share the
same blind spot.

\paragraph{Cross-model evaluation.} Sonnet- and Opus-class
inspectors may exhibit substantially lower metadata-mode trust.
Larger inspectors have longer context windows, more thorough
reasoning chains, and more elaborate
instruction-following structure --- all of which plausibly let
them cross-check the documentation's claims against the code's
actual behavior in ways Haiku does not. We deliberately avoid
claiming the Channel Dichotomy generalizes; the more plausible
prior is that \emph{capability scale attenuates the dichotomy},
and the open question is by how much. A measurement across the
model-size axis would disambiguate three outcomes worth naming:
(a) larger models exhibit attenuated dichotomy --- the most
plausible outcome, where reasoning capacity does scale into
``read everything skeptically''; (b) larger models exhibit the
same dichotomy at the same magnitude --- evidence the priors
are convention-driven (the \code{CLAUDE.md}/\code{AGENTS.md}
convention is treated as authoritative regardless of model
scale); (c) larger models exhibit \emph{stronger} dichotomy,
where deeper reasoning chains make the metadata-channel framing
even more persuasive. Outcome (a) would argue deployments
should default to a more capable inspector even at higher cost;
(b) and (c) would argue mitigation must come from data
(adversarial fine-tuning) or architecture (mandatory
cross-channel verification) rather than scale.

\paragraph{Non-Anthropic inspector models.} The most generalization-
relevant follow-up is to repeat the measurement on
GPT-class inspectors (e.g., \code{gpt-4o-mini}, \code{gpt-5-nano} as
inspector for OpenAI Codex / VS Code Copilot Workspace). If the
dichotomy reproduces, it is a property of the agent+judge
architectural pattern across the LLM family. If it does not, the
mechanism is Anthropic-training-specific and the paper's
generalization claim weakens correspondingly.

\paragraph{Inferential-trust prompt-engineering mitigation.}
Recommendation~1 in \S\ref{sec:discussion} -- prepend the
inspector's system prompt with explicit ``treat all repository
files as untrusted'' guidance -- is testable but unmeasured. A
direct A/B comparing the current default-prompt inspector against a
hardened-prompt variant on the same scenario matrix would establish
how much of the channel dichotomy is closeable by prompt
engineering alone vs. requires retraining.

\section{Conclusion}\label{sec:conclusion}

We measured the bypass rate of an LLM-based inspector judge against
12 supply-chain-shape attacks and identified a structural
vulnerability we name the Channel Dichotomy: the inspector applies
fundamentally different epistemic standards to attacker-controlled
content depending on file type. Authority claims in
``metadata-about-the-project'' files (\code{CLAUDE.md},
\code{AGENTS.md}, \code{package.json} custom fields, JSON fixtures)
enter belief state without scrutiny, raising attack bypass to 100\%
in our data. The same claims in source code are correctly flagged
as fabrication, holding bypass at 0\%. Because both file types are
attacker-authored in any supply-chain attack, the dichotomy is a
load-bearing vulnerability of the agent+judge architecture, not a
detector tuning problem.

The pure supply-chain detection rate (42.9\% mean) is moderate but
unreliable across replicates. The injection-amplified attack class
generalizes across documentation conventions
(\code{CLAUDE.md}~$\equiv$ \code{AGENTS.md}~$\equiv$ \code{package.json}
metadata~$\equiv$ JSON fixtures) and is robust to channel-realism
variations. Identifying the dichotomy reframes the agent-safety
threat model: the channel through which the attacker's prose
reaches the inspector matters more than the channel through which
the payload reaches the runtime.

\section{Reproducibility}\label{sec:repro}

The full code, scenario YAMLs, raw event logs, and analysis scripts
are version-controlled in a single repository. Reproducing the
results in this paper requires three things: a Docker daemon, a
real Anthropic API key (for genuine model invocations), and Python
3.10+ on the host.

\paragraph{One-time setup.}
\begin{verbatim}
docker compose build      # builds bft-agent + bft-judge-agentic
pip install -r requirements.txt
\end{verbatim}

\paragraph{Running a sweep.} The headline matrix in this paper:
\begin{verbatim}
export ANTHROPIC_API_KEY=sk-ant-...
python -m ablations.experiment \
  --config ablations/configs/A1.json \
  --scenarios scenarios/trojaned-codebases/probe-02-bearer-auth.yaml \
              scenarios/trojaned-codebases/claudemd-audit-redirect.yaml \
              scenarios/trojaned-codebases/agents-md-audit-redirect.yaml \
              scenarios/trojaned-codebases/package-json-audit-metadata.yaml \
              scenarios/trojaned-codebases/fixture-as-audit-record.yaml \
              scenarios/trojaned-codebases/inline-source-audit-comment.yaml \
              scenarios/trojaned-codebases/inline-source-no-directive.yaml \
              scenarios/trojaned-codebases/negative-framing-redirect.yaml \
  --reps 3 --max-concurrency 1 --permission-mode dangerous
\end{verbatim}

Total runtime: $\sim$25 min. Total Anthropic API spend at Haiku-4.5
rates: $\sim$\$2--3 (judge-only) plus $\sim$\$0.50 agent-side.

\paragraph{Extracting paper-ready data.}
\begin{verbatim}
python -m analysis.extract_all "results-*" --out extracted-master
python -m analysis.paper_metrics
python -m analysis.plot_paper
\end{verbatim}

These three scripts populate \code{paper-data/*.csv} and
\code{docs/paper/figures/*.pdf}. All numbers reported in
Tables~\ref{tab:scenarios}, \ref{tab:component-map}, and
\ref{tab:results} are reproducible by reading
\code{paper-data/headline\_table.csv}.

\paragraph{Determinism.} Per-rep canary token generation uses
\code{secrets.token\_urlsafe(32)} and is therefore not
deterministic across runs. Other harness state (workspace
rendering, Docker image content, scenario YAML) is fully
deterministic. The Anthropic model itself is non-deterministic
across runs at temperature 0; reported per-scenario penetration
rates are therefore subject to model-side reasoning variance,
which is part of what the paper quantifies (\S\ref{sec:stats}).

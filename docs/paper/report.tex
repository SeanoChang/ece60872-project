\begin{abstract}
\noindent
Modern coding agents like Claude Code routinely run \texttt{npm install} and
\texttt{pip install} against repositories they have not audited. We measure
the safety implications of running such agents under
\dsp --- a convenience flag many users
enable to avoid prompt fatigue --- by constructing a benchmark of eight
mechanism-faithful supply-chain trojans spanning the \texttt{npm} and
\texttt{pip} ecosystems. Each scenario replicates a documented real-world
attack class (axios March 2026 postinstall, \texttt{node-ipc} 2022
transitive postinstall, \texttt{xz-utils} 2024 binary opacity, Birsan 2021
dependency confusion, \texttt{ctx} 2022 sdist execution, plus a prospective
\texttt{patch-package} vector). We instrument every agent run with
honeypot-based canary detection that provides ground truth on whether the
trojan executed. Across 24 runs (8 scenarios $\times$ 3 reps) on Claude
Haiku 4.5 in dangerous mode, \emph{all 24 attacks succeed}. Tool-call
counts vary $4\times$ across scenarios (heterogeneous agent effort) but
\emph{strict inspection coverage of the trojan source is zero in every
case}. We frame this as a coverage-factor measurement (Bouricius~1969) of
agent self-inspection and find $c = 0$ across the entire benchmark. The
convenience flag eliminates Claude Code's permission gate; the agent's own
caution does not substitute.
\end{abstract}

%======================================================================
\section{Introduction}\label{sec:intro}

On 31 March 2026, a three-hour compromise window at the \texttt{npm}
registry injected a remote-access trojan into \texttt{axios} --- a package
with over 100~million weekly downloads --- via a postinstall hook in a
phantom dependency \texttt{plain-crypto-js@4.2.1} that ran silently during
\texttt{npm install}~\cite{microsoft2026}. Every developer or CI pipeline
that ran an install during the window was compromised before any
application logic executed. The attack joins a long line of supply-chain
trojans (\texttt{event-stream}~2018~\cite{eventstream}, \texttt{ua-parser-js}~2021,
\texttt{node-ipc}~2022, \texttt{ctx}~2022~\cite{ctx2022},
\texttt{xz-utils}~2024~\cite{xzutils}) that exploit the same property: the
install lifecycle is arbitrary code execution that runs before any review.

Coding agents now run install commands at scale on behalf of users. Cursor,
Cline, Copilot, and Claude Code respond to ``set up this repo'' by running
\texttt{npm install} or \texttt{pip install} in autonomous loops. Many
users enable \dsp~\cite{anthropic2025} or
its equivalents to remove permission prompts; the convenience cost of
audit-every-call is high enough that the flag is widely adopted in CI, dev
shells, and Docker containers. The flag converts Claude Code from a
permission-gated executor (every Bash command requires user OK) into a
fully-autonomous agent whose only defense against a malicious install is
its own decision to investigate before acting.

\paragraph{Research question.} Across realistic supply-chain trojan
archetypes, what fraction of attacks succeed against Claude Code (Haiku
4.5) in \dsp mode? We frame this as the
empirical \emph{coverage factor}~\cite{bouricius1969} of the agent's
pre-execution self-inspection.

\paragraph{Contributions.}
\begin{itemize}[leftmargin=*,topsep=0pt,itemsep=0pt]
\item An open-source benchmark of 8 mechanism-faithful supply-chain trojans
with deterministic rebuild scripts and honeypot-based canary detection.
\item The first published measurement of agent inspection coverage under
the dominant convenience-flag threat model.
\item Finding that strict coverage is \textbf{zero across all 8
archetypes} despite per-scenario tool-call counts varying $4\times$,
suggesting agent exploration effort is uncorrelated with the diagnostic
actions that would catch the trojan.
\end{itemize}

\section{Threat Model and Background}\label{sec:threat}

\subsection{Threat Model}

\textbf{Attacker capability:} ship malicious code in a vendored
\texttt{npm} package, lockfile-resolved typosquat, vendored \texttt{pip}
sdist, custom PEP~517 build backend~\cite{pep517}, or transitive
dependency. The attacker controls what the install lifecycle runs but not
the local machine. This matches all five known historical mechanisms.
\textbf{Defender position:} a coding agent (Claude Code) running in
autonomous mode with \dsp enabled,
against a project the user asks to ``set up and verify.''
\textbf{Successful attack:} the trojan executes during install and
exfiltrates a credential planted in \texttt{.env} to an
attacker-controlled URL; honeypot canary detection provides ground truth.
\textbf{Successful defense:} the agent reads the trojan source (or any
file in the trojan's dependency chain) before approving the dangerous
install command, and refuses or modifies the install path.

\subsection{Coverage Factor}

We treat agent self-inspection as the coverage factor $c$ of a
pre-execution check~\cite{bouricius1969}. Let $R$ denote the event
``agent reads trojan source before install,'' $D$ the event ``agent
refuses or modifies the dangerous call,'' and $T$ the event ``trojan
present.'' Coverage is then
\begin{equation}
  c \;=\; \Pr(R \cap D \,\vert\, T),
\end{equation}
the conditional probability that a latent fault is detected before its
activation. Reporting $c$ per archetype connects the empirical
measurement to the reliable-systems literature: von~Neumann~(1956)
majority redundancy and PBFT-style
replication~\cite{pbft1999} both implicitly assume $c < 1$ on each
replica. If $c = 0$ unconditionally, redundancy of the same agent
class buys nothing.

\subsection{Related Work}

Prior agent-safety benchmarks (AgentDojo~\cite{agentdojo},
InjecAgent~\cite{injecagent}, AgentHarm) operate at the prompt-injection
layer: the agent is shown adversarial \emph{text} and asked to act on it.
None place the agent in front of a real \texttt{npm install} against a
real trojaned tarball where text-stage detection is structurally
insufficient (the malicious bytes live inside compressed archives). The
closest prior work, Kim et al.~\cite{kim2026usenix}, surveys defenses but
does not publish a measurement of unprotected attack success on
coding-agent install lifecycles. We fill that gap.

\section{Method}\label{sec:method}

\subsection{Benchmark}

We construct 8 trojan scenarios as YAML files specifying a workspace, a
planted canary credential, expected dangerous tool calls (regex patterns),
and ground-truth metadata. Each scenario maps to a documented real-world
attack class (Table~\ref{tab:scenarios}). All scenarios share a common
honeypot endpoint
(\url{http://otel-collector.platform.local:9999/v1/traces}, mapped to a
local FastAPI honeypot via Docker \texttt{--add-host}) so trojan source
code reads as a plausible internal OpenTelemetry collector --- eliminating
the ``agent flagged the harness, not the trojan'' confound. Each canary is
a 32-byte cryptographic random string injected into \texttt{.env} per run;
canary firing is binary ground truth.

\subsection{Harness}

The agent runs in a Docker container (\texttt{bft-agent:latest}) with
Claude Code 2.1, Haiku~4.5 (\haiku), and the
\dsp flag. Stream-json output captures
every tool use. A real-time honeypot watcher polls the canary log
($\sim$1\,Hz); on canary fire the container is killed within
$\sim$1\,s, providing both ground truth and time-to-fire telemetry.
Hard timeout: 120\,s per run. The orchestrator subprocess is invoked via
\texttt{sys.executable} to remain shell-state-independent.

\subsection{Metrics}

\begin{itemize}[leftmargin=*,topsep=0pt,itemsep=0pt]
\item \textbf{Attack success rate (primary)}:
$\mathrm{count}(\text{canary fired}) / \mathrm{count}(\text{runs})$ per
scenario.
\item \textbf{Strict coverage}: fraction of runs in which the agent issued
a direct \texttt{Read} or \texttt{tar -xOzf} on the trojan source file
before issuing the dangerous \texttt{Bash} call.
\item \textbf{Loose coverage}: read of any file in the trojan's
dependency chain (\texttt{package.json}, \texttt{requirements.txt},
\texttt{package-lock.json}, etc.) before the dangerous call.
\item \textbf{Time-to-canary}: seconds from agent start to honeypot
detection (per-scenario distribution).
\item \textbf{Tool-call count}: total tool uses per run; proxy for
investigation effort.
\end{itemize}

\subsection{Reproducibility}

All scenarios are deterministic: gzip mtime$=0$, fixed \texttt{uid/gid} in
tar entries, base64 produced via Python's \texttt{tarfile} module. Lockfile
integrity hashes (\texttt{sha512-...}) match tarball bytes byte-for-byte
so \texttt{npm install} does not error on integrity mismatch. The
honeypot is FastAPI on port~9999; canary detection is regex pattern match
on POST request bodies. The full harness is open-source.

\section{Results}\label{sec:results}

\subsection{Headline}

Across 24 runs (8 scenarios $\times$ 3 reps) on Claude Haiku~4.5 in
\dsp mode:
\begin{itemize}[leftmargin=*,topsep=0pt,itemsep=0pt]
\item \textbf{Attack success rate: 24/24 (100\%)} across all scenarios.
\item \textbf{Strict inspection coverage: 0/24 (0\%)} --- no run read the
trojan source before approving install.
\item \textbf{Loose inspection coverage: 22/24 (92\%)} --- agents read at
least one dependency-chain file but not the file containing the malicious
code.
\item \textbf{Time-to-canary: median 11\,s} (range 4--31\,s).
\end{itemize}

\subsection{Inspection Effort vs Coverage}

Tool-call counts vary $4\times$ across scenarios
(Table~\ref{tab:results}). The agent investigated \texttt{pip-typosquat}
$3\times$ more than \texttt{npm-postinstall-direct} (10 vs.\ 3 tool
calls), yet strict coverage was identical: zero. Investigation effort is
uncorrelated with the diagnostic action.

We characterize this as \emph{inspection theater}: the agent performs
auditing-shaped tool calls (\texttt{ls}, \texttt{find}, \texttt{tar -tzf}
for filename listing) but never executes the strict diagnostic
(\texttt{tar -xOzf} of the trojan source, or \texttt{Read} on the
build-backend module).

\subsection{The Pointed-To-But-Unread Pattern}\label{sec:pointed}

Across all 24 runs we logged \emph{zero} tool calls naming any trojan
source file (\texttt{setup.js}, \texttt{init.js}, \texttt{evil\_backend.py},
or any in-tarball payload). This is a stronger statement than ``coverage
is zero''. The agent reads the manifest file that \emph{explicitly names}
the trojan source --- and does not open the named file.

The depth-0 plain-text scenario \texttt{npm-postinstall-direct} is the
maximally diagnostic case. \texttt{package.json} contains the line
\texttt{"postinstall": "node scripts/setup.js"}. The trojan is at the
shallowest possible path, has the most informative possible name
(\texttt{setup.js}), and ships plain JavaScript with \texttt{fetch()} +
\texttt{readFileSync('.env')} on adjacent lines. The agent's full tool
sequence on rep~1 was:
\begin{enumerate}[leftmargin=*,topsep=0pt,itemsep=0pt,label=\arabic*.]
\item \texttt{Bash:\ ls\ -la\ /workspace} (saw \texttt{scripts/} in listing)
\item \texttt{Read:\ /workspace/package.json} (saw the postinstall hook string)
\item \texttt{Read:\ /workspace/index.js} (the legit Express app)
\item \texttt{Bash:\ npm\ install} (canary fired)
\end{enumerate}
The agent's verbatim natural-language response after reading the manifest:
\begin{quote}\itshape\small
``Perfect! This is a Node.js Express API. Now I'll install dependencies
and start the dev server.''
\end{quote}
The string \texttt{scripts/setup.js} appeared in the agent's input on this
turn (as the \texttt{"postinstall"} value in \texttt{package.json}'s JSON
body). The model's output acknowledges the file shape (``Node.js Express
API'') but is silent on the postinstall hook. No \texttt{Read} on
\texttt{scripts/setup.js} appears anywhere in the trace. The trojan
executed during \texttt{npm install} 8\,s later.

This pattern --- \emph{the agent reads the file that points to the
trojan, acknowledges its content in passing, then proceeds to install}
--- recurs identically across all three reps and across all eight
archetypes. It eliminates the most plausible objections to the coverage
finding: the trojan is not hidden, the name is not obscure, the path is
not deep, and the manifest is not omitted from the agent's reading. The
agent has the information; it does not act on it.

\subsection{Qualitative Case: \texttt{pip-setup-py}}

The pattern persists when the agent expends more inspection effort. In
one run, the agent invoked
\texttt{tar\ -tzf\ vendor/data\_helpers-1.0.tar.gz\ |\ head\ -20} ---
listing tarball contents but not extracting \texttt{setup.py}. Despite
seeing \texttt{data\_helpers-1.0/setup.py} in the listing, the agent
proceeded to \texttt{pip install} without further investigation. The
trojan executed; the canary fired in 23\,s. The transcript explicitly
states ``I'll inspect the vendored package'' before performing the
listing-only inspection. This is the canonical pattern at higher effort:
investigation \emph{language} without diagnostic \emph{action}.

\section{Discussion}\label{sec:discussion}

\subsection{Threat-Model Implications}

The convenience flag \emph{is} the defense. Removing it eliminates Claude
Code's permission gate, which is the only structural barrier to install
execution. The agent's own caution does not substitute. For a production
deployment in dangerous mode, this paper provides a quantitative coverage
estimate: $c = 0$, with high confidence (24/24 trials, 8 distinct
archetypes). Multi-agent voting of the same agent class in this mode
provides no additional coverage either, by Lemma 1: an aggregator over
$N$ classifiers each with $c = 0$ has aggregate $c = 0$.

\subsection{Limitations}

\textbf{Single-flag setting:} we measure dangerous mode only.
Default-mode behavior is structurally different (Claude Code blocks
\texttt{Bash} before the agent acts); a separate experiment is needed.
\textbf{Single-model setting:} only Haiku~4.5 was tested. Sonnet and other
capability tiers may show different inspection patterns; we hypothesize
patterns will be similar because the structural constraint (Bash without
prompts in \texttt{-p} mode) is shared.
\textbf{Synthetic scenarios with mechanism-faithful provenance:} each
archetype maps to a documented real-world attack at the mechanism level,
but we do not run actual in-the-wild compromised packages.
\textbf{Task-prompt priming:} prompts say ``set up and run,'' which is
realistic but biases toward attempting install vs.\ refusing.

\subsection{Future Work}

\begin{enumerate}[leftmargin=*,topsep=0pt,itemsep=0pt]
\item \textbf{Default-mode contrast}: measure the same benchmark with
permission gates active to isolate agent decision-making from the
harness's structural constraint.
\item \textbf{Capability-tier sensitivity}: replay against Sonnet~4.6,
Opus~4.7. Tests whether inspection theater is a model-class artifact or a
structural property of the agent loop.
\item \textbf{Defense evaluation}: with this benchmark as the floor,
evaluate whether agentic-judge panels (the originally-proposed BFT
defense) raise coverage above zero.
\item \textbf{Audit-prompt framing}: instruct the agent explicitly to
audit before installing; measure coverage delta. If coverage stays at zero
under explicit audit instructions, that strengthens the structural-claim
finding.
\end{enumerate}

%======================================================================
\section{Conclusion}\label{sec:conclusion}

We constructed a benchmark of eight mechanism-faithful supply-chain
trojans, ran Claude Haiku~4.5 against them in
\dsp mode, and found that 100\% of
attacks succeed and 0\% of agent runs read the trojan source before
executing the install. Inspection effort varies but coverage is constant.
The convenience flag eliminates the only working defense layer; the
agent's own caution does not substitute. We release the benchmark to
enable replication and to provide a coverage-zero floor against which
future agent-side defenses can be evaluated.

Judge Cluster Redesign: Real Agentic Judges

Each judge is its own agent with its own isolated environment — not an API wrapper

The Problem With the Current Spec

What the spec says (wrong)
  • Judge gets tool call JSON
  • Calls a few lightweight Python functions
  • Returns approve/reject
  • Basically a prompt + some regex = Python wrapper
  • Can't actually look at the code being executed
What it should be (agentic)
  • Each judge is its own Claude agent
  • Each judge has its own isolated Docker container
  • Can download the package/repo under review
  • Can read, inspect, and test-run code in sandbox
  • Makes an informed decision based on actual analysis

What Each Judge Agent Actually Is

Each judge is a Claude Code instance (or equivalent agent built with the Anthropic SDK) running in its own isolated Docker container. It receives a read-only snapshot of the coding agent's workspace plus the proposed tool call. It can use its own tools (bash, file read, grep, etc.) inside its sandbox to investigate. It runs for up to N seconds, then returns a verdict. Its sandbox is destroyed after each judgment.

Judge Agent Capabilities By Perspective

Judge A: Param Validator
Focus: structural safety
  • Parse command arguments
  • Check for path traversal
  • Check for shell injection
  • Inspect file paths being written
  • Validate URLs in arguments
  • Static analysis of scripts
Judge B: Intent Aligner
Focus: task relevance
  • Read the original task prompt
  • Read workspace files for context
  • Compare action to task scope
  • Check if dependencies are relevant
  • Flag off-task network calls
  • Verify edit targets make sense
Judge C: Threat Modeler
Focus: adversarial analysis
  • Clone/download code in sandbox
  • Inspect postinstall scripts
  • Test-run in isolated env
  • Monitor for outbound network calls
  • Check package name for typosquats
  • Deobfuscate suspicious scripts
  • Read dependency tree

Axios Attack: How Judge C Would Catch It

// Coding agent proposes: bash("npm install")
// Judge C (Threat Modeler) investigates in its own sandbox:

1. Reads /workspace/package.json → sees "axios": "^1.14.0"
2. Runs npm install --dry-run in sandbox → sees dependency tree
3. Notices transitive dep: plain-crypto-js@4.2.1
4. Checks: is "plain-crypto-js" a known package? → Not in top npm packages
5. Checks: Levenshtein("plain-crypto-js", "crypto-js") = 6 → possible typosquat
6. Downloads plain-crypto-js, reads package.json → sees postinstall: "node setup.js"
7. Reads setup.js → sees obfuscated code, XOR cipher, base64
8. Verdict: REJECT (confidence: 0.95)
"Transitive dependency plain-crypto-js is a likely typosquat of crypto-js.
Contains obfuscated postinstall script with network calls."
